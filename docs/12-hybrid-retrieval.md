# 하이브리드 근거 검색 (키워드 + 벡터)

## 지금 구조

근거 찾기는 세 단계다.

1. 규칙 매핑(`lookup_claim_rules`): 버전 관리되는 규칙 표가 주장 유형과 문구 패턴에 맞는 조항을 붙인다. 법령 조항은 대부분 여기서 온다.
2. 하이브리드 검색(`search_regulations`): 규칙이 이름 붙이지 않은 지침, 해설서, 협회 기준을 보충한다.
3. 사례 검색(`search_precedents`): 참고용, 같은 하이브리드 검색을 쓴다.

하이브리드 검색은 두 순위를 합친다.

- 키워드: 한글 두 글자 단위 BM25. 조문 번호와 법률 용어처럼 정확한 표현에 강하다.
- 벡터: OpenAI `text-embedding-3-small`을 1024차원으로 받아 pgvector에 저장하고 질문도 같은 모델로 임베딩한다. 표현이 달라도 뜻이 가까운 조각을 찾는다.
- 합치는 방식: RRF(reciprocal rank fusion, k=60, 두 순위 같은 가중치). 아래 비교로 골랐다.

검색 결과는 `keyword_score`(질문 두 글자 묶음이 조각에 있는 비율)와 `vector_score`(코사인)를 따로 낸다.
척도가 달라서 Agent도 기준값을 따로 쓴다(`regulations.py`): 키워드 0.45 이상이거나 벡터 0.45 이상이면 근거로 쓴다.

## 적재 상태 (2026-10-21 로컬)

| 항목 | 값 |
| --- | --- |
| 문서 버전 | 17건 (규칙 16, 사례 1) |
| 조각 | 1,099개, 전부 임베딩 |
| 모델 | text-embedding-3-small, 1024차원 (`embedding_model`, `embedding_revision=dim1024`로 조각마다 기록) |
| 처음 적재 시간과 비용 | 약 30초, 약 78만 자(1백만 토큰 미만), 수십 원 수준 |

조각 하나(화장품 안전기준 제6조, 9,031자)는 OpenAI 입력 한도(8,192토큰)를 넘어서, 임베딩할 때만 앞 6,000자를 쓴다.
키워드 검색과 근거 발췌는 조각 전체를 그대로 쓴다.

## 전후 비교

`python -m capstone_rag_mcp.compare`로 다시 만들 수 있다. 광고 주장 14개를 Agent가 실제로 보내는 질문(문구와 주장 유형별 법령 표현)으로 검색했다.

- 관련도: 상위 3개 조각마다 모델(gpt-5.4-mini)이 "이 주장을 검토하는 데 직접 근거가 되는가"를 판정했다.
- 규칙 일치: 상위 3개 안에 규칙 표가 지정한 조항이 있는가.
- Agent 근거: Agent가 기준값을 통과한 첫 조각 하나를 근거로 붙이는데, 그 수와 그중 관련 있음 판정 수.

| 방식 | 상위 3개 관련도 | 규칙 일치 | Agent가 붙이는 검색 근거 |
| --- | --- | --- | --- |
| 키워드만 (이전) | 36/42 | 14/14 | 10건, 관련 10 |
| **하이브리드 RRF (채택)** | 32/42 | 11/14 | **14건, 관련 13** |
| 하이브리드 계단식 | 25/42 | 9/14 | 14건, 관련 11 |
| 하이브리드 키워드순 + 벡터 확인 | 38/42 | 14/14 | 11건, 관련 11 |

대조군(광고가 아닌 문장: 배송 안내, 고객센터 안내, 분리배출 안내)의 벡터 최고 코사인은 0.31~0.38,
광고 주장은 0.45~0.63이었다. 벡터 기준값 0.45는 이 사이에 둔 값이다.

### 어떻게 읽나

- 순위만 보면 키워드가 낫다. RRF는 규칙이 지정한 법령 조항을 상위 3개 밖으로 밀어낸 경우가 있다.
  하지만 그 조항은 규칙 매핑이 이미 붙이고, 검색은 같은 조항을 다시 붙이지 않는다. 검색의 역할은 지침과 해설서를 보충하는 것이다.
- Agent가 실제로 붙이는 근거는 RRF가 가장 많다(관련 있는 근거 10건에서 13건). 키워드 일치율이 낮아 버려지던 조각을 벡터 점수로 살린다.
  예: "*연구기관: (주)프로브엠 피부임상연구센터"는 키워드 0.15로 버려졌지만 벡터 0.58로 표시, 광고 관리 지침이 붙었다.
- 키워드순 + 벡터 확인은 상위 3개가 키워드와 같다. 관련도 36과 38의 차이는 판정 모델의 흔들림이다(같은 목록을 두 번 판정해 ±2 차이를 확인함).

### 한계

- 주장 14개는 작은 표본이다. 판정 모델 하나의 판단이라 ±2 정도 흔들린다.
- 광고자문 해설서의 일반 조각 하나가 여러 주장의 가까운 벡터 이웃으로 자주 나온다. 조각을 더 잘게 나누면 나아질 수 있다.
- 실제 광고 묶음에 사람이 정답 조항을 단 평가셋은 아직 없다.

## 켜고 끄기, 배포

- `RAG_EMBEDDING_MODEL`: 비우면 compose가 `text-embedding-3-small`을 쓴다. `off`면 키워드 검색만 한다.
  로컬 모델(예: `BAAI/bge-m3`)도 되지만 ingest extra(sentence-transformers, CPU torch)가 필요하고 이미지가 수 GB 커진다.
- rag-mcp와 rag-ingest에 `OPENAI_API_KEY`가 있어야 한다. 질문 임베딩은 검색 한 번에 API 한 번(0.1~0.3초)이다.
- 이미 적재된 DB는 원본을 다시 받지 않고 임베딩만 채운다.

```sh
docker compose run --rm rag-ingest uv run --no-sync python -m capstone_rag_mcp.batch embed
```

  벡터가 없는 조각과, 다른 모델로 만든 조각만 다시 임베딩한다. 중간에 끊겨도 문서 단위로 저장돼 다시 돌리면 이어서 한다.
- `rag-ingest` 기본 명령(`all --if-empty --embed`)도 빈 DB면 전부 적재하고, 이미 있으면 임베딩만 채운다.
- 배포 환경도 같다. rag-mcp 서비스에 `OPENAI_API_KEY`와 `RAG_EMBEDDING_MODEL`을 넣고, 배포 DB를 가리키는
  `RAG_INGEST_DATABASE_URL`로 위 `embed` 명령을 한 번 실행한다.
