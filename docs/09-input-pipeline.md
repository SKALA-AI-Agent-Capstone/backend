# 광고 입력과 문서 처리 설계

> 문서 상태: 팀 검토용 구현안. 아래 파서, Vision 호출, 업로드 API와 오류 처리는 아직 구현되지 않았다.
> 제품 요구사항: [노션 기획서](https://app.notion.com/p/Agent-3fe616ab8fec80bfb92df115c66aa83d)의 FR-1, FR-3, FR-7, FR-8, FR-10 및 NFR-3, NFR-10, NFR-12.

## 1. 먼저 구분할 세 가지 작업

| 작업 | 하는 일 | 예 |
| --- | --- | --- |
| PDF 파싱 | 파일 안에 이미 들어 있는 문자와 표, 위치를 읽는다 | 텍스트 PDF의 문구와 각주 추출 |
| OCR | 이미지 픽셀에서 글자를 인식한다 | 스캔 PDF의 시험 결과 숫자 읽기 |
| Vision 분석 | 이미지의 문자뿐 아니라 사진, 그래프와 배치의 의미를 해석한다 | 문구와 전후 사진, 각주가 함께 주는 인상 분석 |

PDF 확장자만 보고 OCR 여부를 정하지 않는다. 같은 PDF 안에서도 페이지와 영역에 따라 텍스트와 이미지가 섞인다.
OCR로 글자를 읽었다고 광고의 시각적 문맥까지 검토한 것은 아니다.

## 2. 이 프로젝트의 기준 구현안

노션은 Vision LLM 또는 OCR + LLM을 허용하며 특정 OCR 제품은 정하지 않았다.
초기 구현은 로컬 PDF 파싱과 Vision API를 조합한다. 정확한 하이라이트 좌표가 필요한 경우 로컬 OCR을 확장한다.
이 선택은 노션 확정 사항과 구분되는 개발 제안이다.

사용자에게 제공하는 광고 입력은 PDF 파일과 이미지 파일 두 종류다.
텍스트와 스캔 여부, 혼합 페이지와 긴 이미지는 서버가 내부에서 구분한다.
직접 카피 입력 UI는 제외한다. 합성 문장을 쓰는 Claim 테스트는 개발용 내부 경로다.

| 입력 파일 | 서버 내부 유형 | 로컬 전처리 | AI 처리 | 위치 정보 |
| --- | --- | --- | --- | --- |
| PDF | 텍스트 페이지 | pdfplumber로 문자, 표와 좌표 추출 | 광고 페이지의 시각 문맥은 렌더 이미지도 Vision으로 확인 | PDF 좌표를 화면 좌표로 변환 |
| PDF | 스캔 페이지 | pypdfium2로 페이지를 이미지로 렌더 | Vision으로 문자와 시각 문맥 추출 | 기본은 페이지 단위, 정확한 좌표는 별도 OCR |
| PDF | 텍스트와 스캔 혼합 | 페이지와 영역별로 파싱 여부 판단 | 문자 추출이 부족한 영역과 시각 요소를 Vision으로 확인 | 추출 방법과 좌표 출처를 함께 보관 |
| 이미지 | 일반 PNG 또는 JPEG | 디코딩, 회전과 픽셀 크기 확인 | Vision으로 문자와 시각 문맥 추출 | 기본은 이미지 단위, 정확한 좌표는 별도 OCR |
| 이미지 | 세로로 긴 상세페이지 | 겹치는 타일로 분할, 원본 좌표 변환 기록 | 타일별 분석 후 문구와 각주를 다시 연결 | 원본 이미지 좌표로 환산 |

텍스트 PDF에서도 이미지 안에만 들어 있는 문구를 놓칠 수 있다. 문자 추출 성공을 페이지 전체 검토 완료로 취급하지 않는다.
중복 추출은 페이지와 좌표 및 원문을 기준으로 통합하고, 각주를 본문 주장과 연결한다.
광고와 증빙 각각의 파일 유형에 따라 전처리와 Vision 경로를 적용한다.
모든 파일을 광고라고 가정하지 않고 ADVERTISEMENT와 SUPPORTING_DOCUMENT를 구분해 같은 전처리 모듈을 사용한다.

### 사용할 패키지와 실행 위치

| 항목 | 기준안 | 실행 위치 | 현재 설치 및 구현 상태 |
| --- | --- | --- | --- |
| PDF 문자와 표 | pdfplumber | business-mcp 내부 공통 문서 준비 모듈 | RAG 수집용 선택 의존성에만 있음, 고객 입력 처리 미구현 |
| PDF 페이지 렌더 | pypdfium2 | 같은 문서 준비 모듈 | 신규 도입 제안 |
| 이미지 확인과 타일 분할 | Pillow | 같은 문서 준비 모듈 | 입력 처리 모듈 미구현 |
| 문자와 시각 문맥 인식 | OpenAI Responses API의 이미지 입력 예시 | Agent의 Vision adapter | SDK와 호출 미구현, 실호출 없음 |
| 정확한 글자 좌표 | Tesseract와 한국어 학습 데이터 후보 | business-mcp 내부 OCR adapter | 선택 확장, 평가 후 채택 |
| 주장 구조화와 검토 | LangGraph 노드와 Pydantic | Agent | 계약 외 업무 노드 미구현 |

OpenAI는 설명을 구체화하기 위한 공급자 예시다. 특정 모델은 고정하지 않고 VISION_MODEL과 TEXT_MODEL로 설정할 계획이다.
모델은 이미지 입력 및 필요한 구조화 출력 지원을 확인한 뒤 선정한다.
로컬 OCR 후보는 실제 한국어 광고와 작은 각주로 평가해야 한다. OCR을 켜도 사진 해석을 대신하지 않는다.

## 3. API 키는 어디에서 쓰나

| 기능 | 자격증명 | 키 보관 위치 |
| --- | --- | --- |
| 로컬 PDF 파싱과 이미지 렌더 | 외부 API 키 없음 | 해당 없음 |
| 로컬 Tesseract OCR | 외부 API 키 없음, 엔진과 언어 데이터 필요 | 해당 없음 |
| Vision API와 텍스트 LLM | 예시: OPENAI_API_KEY | Agent 서버의 비밀 환경변수 |
| 다른 공급자의 관리형 OCR을 선택하는 경우 | 해당 OCR 서비스 키 | 그 adapter를 실행하는 서버 |
| 식약처와 KIPRIS Plus | 서비스별 신청 및 인증 정보 | business-mcp 서버 |
| 현재 준비값인 로컬 bge-m3 임베딩 | LLM API 키 없음, 모델 실행환경 필요 | 수집 배치와 RAG 검색 서버 |
| 내부 HTTP와 MCP | 내부 서비스 토큰과 인증된 기업 범위 | 서버 간 통신에만 사용 |

ChatGPT 로그인이나 구독을 이 애플리케이션의 API 키로 사용하지 않는다.
브라우저가 LLM을 직접 호출하거나 VITE_*에 키를 넣지 않는다. 내부 서비스 토큰도 LLM 키와 다르다.
위 공급자 변수는 설계안이며 현재 서버가 읽거나 실제 요청을 보내는 설정은 아니다.

## 4. 원본 파일이 움직이는 실제 경계

광고 원본과 비공개 증빙은 업무 데이터이므로 Agent가 Redis나 업무 DB에서 직접 꺼내지 않는다.
다음은 아직 구현하지 않은 인터페이스 제안이다.

~~~mermaid
sequenceDiagram
  participant V as Vue
  participant B as Backend
  participant R as Redis 원본 캐시
  participant A as Agent 입력 노드
  participant M as business-mcp
  participant P as 로컬 문서 준비 adapter
  participant L as Vision API
  V->>B: 광고와 증빙 업로드
  B->>B: 파일 검증, 기업 권한, asset ID와 해시 생성
  B->>R: 처리 중 원본 임시 저장
  B->>A: task ID, 광고 버전, 인증 범위와 asset ID
  A->>M: MCP prepare_input(asset ID)
  M->>B: 인증된 내부 파일 읽기 API
  B->>B: task와 tenant에 속한 asset인지 재검증
  B->>R: 임시 원본 읽기
  R-->>B: 임시 원본 바이트
  B-->>M: 소유 범위를 검증한 원본
  M->>P: 페이지 파싱, 렌더와 필요 시 OCR
  P-->>M: 문자 블록, 페이지 정보, 분석용 이미지
  M-->>A: 구조화된 추출 결과와 제한된 이미지 콘텐츠
  A->>L: 필요한 이미지와 문맥, 서버 API 키
  L-->>A: 문자, 시각 관찰과 주장 후보
  A->>A: 출력 형식 검증, 판독 불가와 누락 검사
~~~

prepare_input은 business-mcp에 추가할 제안 이름이며 현재 등록된 도구가 아니다.
task와 기업 범위는 Backend가 발급한 실행 문맥에 고정하고 모델이 도구 인자로 바꿀 수 없게 한다.
내부 asset API는 서비스 토큰만 확인하지 않고 해당 실행 문맥의 task와 asset 소유 관계도 검증한다.
현재 개발용 정적 토큰에는 이 사용자 및 기업 권한 기능이 없으므로 업무 데이터 연동 전에 구현해야 한다.
일반 파일 해석 코드는 business-mcp의 공통 모듈이 소유하고 Agent는 호출 순서와 결과 검증을 소유한다.
광고와 증빙에 동일한 파서 코드를 복사하지 않는다. RAG의 공개 문서 수집은 별도 배치다.

MCP가 OCR이나 이미지 인식을 해주는 것은 아니다. 위 준비 함수를 Agent가 호출할 수 있게 노출하는 연결 방식이다.
Vision 요청은 Agent에서 공급자 API로 보내는 HTTPS 호출이며 MCP 요청과 별개다.
원본의 base64를 로그나 일반 모델 메시지, Graph 체크포인트에 그대로 저장하지 않는다.
MCP 결과의 이미지 콘텐츠는 Client adapter가 필요한 Vision 요청에만 넣는다. 파일 전체를 무제한 도구 응답으로 반환하지 않는다.

## 5. 입력 검증과 판독 품질

### 접수 전 검증

- 파일명 확장자, 실제 MIME과 디코딩 결과를 함께 확인한다.
- 암호화 또는 손상 PDF, 지원하지 않는 형식은 AI 호출 전에 거절한다.
- 파일 용량, 누적 용량, PDF 페이지 수와 이미지 픽셀 수를 제한한다.
- 초기 제안 한도는 파일 10 MiB, 작업 합계 30 MiB, PDF 20페이지다. 노션의 확정 수치도 현재 적용된 제한도 아니다.
- 해제된 이미지와 PDF 렌더 결과는 파일 바이트보다 커질 수 있으므로 픽셀 수와 작업 메모리도 따로 제한한다.
- 파싱은 시간과 메모리가 제한된 실행 단위에서 수행한다. 문서 안의 명령을 시스템 지침으로 실행하지 않는다.

### 판독 품질 확인

- 빈 문자, 깨진 문자, 페이지와 문구 누락, 숫자와 단위의 충돌을 검사한다.
- 모델이 말한 자신감 수치를 OCR 정답 확률로 쓰지 않는다.
- OCR confidence가 있으면 엔진과 측정 단위를 기록한다. 다른 엔진 수치를 그대로 비교하지 않는다.
- Vision이 제안한 좌표는 정밀 OCR 좌표와 구분한다. 검증된 좌표가 없으면 페이지 단위로 보여준다.
- 작은 각주나 수치가 불명확하면 해당 영역을 한 번 보강해 읽고, 여전히 불명확하면 사용자 확인을 요청한다.
- 일부 페이지가 판독되지 않았으면 전체 광고를 검토 완료로 표시하지 않는다.
- Pydantic 통과는 응답 형식이 맞다는 뜻이다. 읽기 정확도나 판단의 타당성을 보장하지 않는다.

## 6. 공통 추출 데이터 제안

현재 Pydantic 검색 계약과 별개인 후속 계약이다. 구현 시 packages/shared에서 먼저 합의한다.

~~~json
{
  "asset_id": "asset-demo-01",
  "asset_role": "ADVERTISEMENT",
  "page": 1,
  "block_id": "block-demo-01",
  "text": "SPF50+ PA++++, 물놀이 두 시간에도 차단력 유지",
  "extraction_method": "VISION",
  "bbox": null,
  "coordinate_source": "UNAVAILABLE",
  "quality_status": "NEEDS_CONFIRMATION",
  "warnings": ["각주 영역 판독 확인 필요"]
}
~~~

asset_role은 ADVERTISEMENT 또는 SUPPORTING_DOCUMENT로 구분한다.
고객 광고의 추출 결과는 PDF 또는 이미지 asset에 연결한다. 내부 합성 테스트를 별도 제품 입력 기능으로 노출하지 않는다.
광고에 대한 주장은 원문과 주변 문맥, block ID, 각주 참조를 함께 가진다.
검증된 bbox는 원본 페이지 기준 왼쪽 위 원점의 0~1 좌표로 통일하고 렌더 크기와 회전 변환을 기록한다.
광고 페이지와 법령 근거의 페이지 번호는 서로 다른 필드다.

## 7. 입력별 예외 처리

| 상황 | 처리 | 화면 상태 | 재시도 범위 |
| --- | --- | --- | --- |
| 손상, 암호 PDF 또는 형식 불일치 | 접수 중단, 새 파일 요청 | INPUT_REJECTED | 업로드만 다시 |
| 텍스트 PDF의 특정 페이지만 스캔 | 해당 페이지 렌더와 Vision | 해당 페이지 처리 중 | 해당 페이지만 |
| 흐린 이미지, 숫자 또는 각주 불명 | 보강 후 사용자 수정 또는 재업로드 | WAITING_INPUT | 해당 페이지와 영향받는 주장 |
| Vision API 429 또는 일시 장애 | 제한된 재시도, 그래프 상태 보존 | 재시도 중 또는 FAILED | 해당 노드만 |
| Vision 키 누락 또는 인증 실패 | 서버 설정 오류로 종료, 사용자 잘못으로 표시하지 않음 | 처리 설정 오류 | 설정 복구 후 해당 노드 |
| 증빙 미제출 | 필요한 자료 목록 생성, 근거 있는 부분은 검토 | 자료 보완 필요 | 증빙 대조와 영향받는 판단 |
| 공공 API 정상 응답에 품목 없음 | 미조회로 기록, 제품 부재로 단정하지 않음 | 확인 필요 | 조회 또는 사용자 확인 |
| 공공 API 장애 | 실패한 항목만 미확인, 다른 검토 유지 | 부분 결과 | 실패한 조회만 |
| 법령 검색 결과 없음 | 근거 부족, 자동 적합 처리 금지 | 근거 확인 필요 | 질의 보강 또는 담당자 검토 |
| 처리 중 캐시 원본 소실 | 이미 완료한 추출을 보존, 필요 원본만 요청 | WAITING_INPUT | 동일 파일 재확보 후 |
| 승인 요청 뒤 광고 수정 | 새 ad_version_id, 이전 승인 적용 금지 | 재검토 필요 | 새 버전 기준 |

제한된 재시도 횟수와 대기시간은 공급자와 오류 종류별 설정으로 둔다. 문서에 임의의 보장 시간을 쓰지 않는다.

## 8. 원본 폐기와 승인 화면의 관계

노션은 업로드 원본 임시 보관과 검토 결과 영구 보존을 요구한다.
따라서 과거 이력에서 원본 이미지를 항상 다시 볼 수 있다고 약속하면 안 된다.

기준 제안은 초안 생성과 필요한 추출 완료 후 서버 원본을 폐기하고, 결과에 원문 텍스트와 인용, 파일 해시를 남기는 것이다.
같은 브라우저는 사용자가 선택한 로컬 파일을 미리보기로 유지할 수 있지만 새 브라우저나 다른 승인자에게 자동 전달되지는 않는다.
승인자가 시각 원본을 확인해야 하는데 파일이 없으면 재업로드를 요청한다.
해시가 같은 경우 기존 버전에 연결해 열람하며 LLM 재실행이나 중복 차감을 자동 발생시키지 않는다.
다른 파일이면 새 버전으로 재검토한다. 승인 종료까지 원본을 유지할지 여부는 보존 정책의 팀 결정이 필요하다.

체크포인트에는 원본 바이트나 이미지 대신 ID와 최소 파생 데이터만 둔다.
외부 Vision 공급자에게 전송한 데이터의 보존 정책은 우리 Redis 삭제와 별개다.
OpenAI의 store=false만으로 모든 외부 보존이 사라진다고 설명하지 않는다. Files API를 쓰면 파일 수명과 삭제도 별도로 관리한다.

## 9. 구현 전 통과할 예제

- 같은 광고의 텍스트 PDF, 스캔 PDF와 PNG에서 핵심 주장과 각주 연결 비교.
- 세로로 긴 이미지의 타일 경계에서 문구가 중복되거나 사라지지 않는지 확인.
- 보습 수치, 시험 기간, 단위와 특허번호가 흐릴 때 확인 요청으로 전환되는지 확인.
- 원본이 만료된 작업 재시도와 승인 화면의 재업로드 흐름 확인.
- 다른 기업의 asset ID를 넣어도 내부 API가 읽기를 거부하는지 확인.
- Vision 장애와 일부 공공 API 장애가 구분되고 적합 판정으로 바뀌지 않는지 확인.

## 10. 공식 기술 자료

- [OpenAI 이미지 입력](https://developers.openai.com/api/docs/guides/images-vision): 서버에서 이미지와 문자를 함께 분석할 수 있으며 작은 문자, 한국어와 정밀 위치 해석에는 한계가 있다.
- [OpenAI 파일 입력](https://developers.openai.com/api/docs/guides/file-inputs): 지원 모델에 PDF를 직접 보내는 대안도 있다. 파일과 페이지 전체가 처리되므로 선택 전 비용과 위치 추적을 비교한다.
- [OpenAI 데이터 처리](https://developers.openai.com/api/docs/guides/your-data): 외부 공급자의 데이터 수명은 내부 캐시 수명과 구분한다.
- [pdfplumber](https://github.com/jsvine/pdfplumber): 문자, 표와 위치를 읽는 로컬 파서. 이미지 OCR 엔진과 다르다.
- [pypdfium2](https://pypdfium2.readthedocs.io/en/stable/python_api.html): PDF 페이지를 이미지로 렌더하는 로컬 라이브러리.
- [Tesseract API](https://tesseract-ocr.github.io/tessdoc/APIExample): 글자 인식과 단어 위치 및 confidence를 제공하는 로컬 OCR 후보.

## 10. 최신 Graph 초안과 입력 준비 제안의 관계

2026-10-20에 확인한 노션 Graph는 Agent 입력 노드가 Vision LLM을 직접 호출하고,
이후 탐지와 근거 검색, 증빙 및 공식 조회는 제한된 도구선택 loop로 수행한다고 명시한다.
위 prepare_input은 PDF 파서와 파일 전달을 구체화한 기존 팀 검토용 제안이며 노션 확정 도구가 아니다.
Agent가 MCP로 제한된 asset을 받는 방식과 Backend 내부 전달 중 어떤 입력 경계를 쓸지는
Agent, Backend와 Business MCP 담당자의 입력 계약 PR에서 결정한다. Agent에 Redis 비밀번호를 추가하지 않는다.
이번 초기 설정에서 OCR, Vision이나 prepare_input을 새로 구현하지 않았다.
